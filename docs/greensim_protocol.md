# Проверка гипотезы на Green Challenge

Здесь три проверки и список сабмитов. Каждая проверка даёт число, которое может гипотезу опровергнуть.
Всё опирается на инструменты из моего репозитория `green_challenge`: `gch.eval_offline`, `gch.inspect_wbc`, рекордер `GC_RECORD_DIR` и бенч `bench/run.sh`.

## A. Офлайн-темп чекпойнтов (Kaggle 2× T4, около 4 ч, симулятор не нужен)

Проще всего запустить одной командой на сервере с GPU: `GC_TOOLKIT=~/green_challenge CKPT=~/ckpt bash greensim/server_check.sh`.
Скрипт ставит окружение (или берёт готовое через `PYTHON=`), накладывает патч на копию моих инструментов и скачивает по 6 scripted-эпизодов трёх оценочных сцен (кольцо, сахарница, газировка; меньше 1 ГБ). Потом прогоняет `eval_offline` и печатает таблицу для A и A2. Ниже то же самое по шагам.

Что ожидаю (H3): у ft1 запланированный темп, то есть насколько далеко уходит план за 0.5 с по сравнению с демонстрацией, ниже, чем у бейзлайна, хотя офлайн-ошибка ниже. Порядок чекпойнтов на лидерборде должен лучше совпадать с порядком по темпу, чем по ошибке.

```bash
cd green_challenge && patch -p1 < ../vla-closed-loop-gap/greensim/eval_offline_tempo.patch
GREENVLA_ROOT=~/GreenVLA python -m gch.eval_offline --data <held-out scene roots> \
    --checkpoint ckpt/014814 --checkpoint ckpt_ft1 --checkpoint ckpt_ft2 --checkpoint ckpt_ft3 \
    --episodes-from runs/ft1/run.json --stride 30 --precision float16 --out eval_tempo.json
```

Патч добавляет в отчёт `planned_tempo` по группам суставов (`torso_arms_neck`, кисти): отношение пути плана к пути демонстрации на строках 2…17 (0.5 с) в тех кадрах, где демонстрация движется. Смотреть лучше на сценах, похожих на оценочные (ring из scripted, darkstore, plate).

Сравнивать надо чекпойнты между собой на одних и тех же кадрах, то есть `plan_over_demo` у ft1 делить на `plan_over_demo` у бейзлайна. На teleop-эпизодах сама демонстрация медленная, и модель, которая её копирует, получит около 1, хотя по сравнению с бейзлайном она медленнее.

Гипотеза не подтверждается, если темп ft1 не ниже, чем у бейзлайна (в пределах ±3 %). Тогда падение ft1 на лидерборде объясняется чем-то другим, например сдвигом сцен.

### A2. Почему не помог adaptive15 (тот же прогон)

Тот же патч печатает `finger events`: какую долю строк мой детектор адаптивной скорости (ход любого пальца больше 0.01 рад между соседними строками) помечает как захват или отпускание, отдельно для сэмплированных планов и для демонстраций. В TempoBench в демо-чанках помечено 2 % строк, в планах политики 60 %. С окном ±10 строк на скорости 1× остаётся 99 % строк, и адаптивная скорость фактически выключается: скор совпадает со скором без неё.

Что ожидаю: у бейзлайна `rows_kept_slow` для планов близко к 1.0, а для демо заметно меньше. Тогда adaptive15 (15.358) на деле был бейзлайном (15.445) плюс шум, и идею SAIL он не опровергает. Если же у планов `rows_kept_slow` около 0.6 или меньше, адаптивная скорость работала и действительно не помогла.

Исправление — `[greensim/action_feed_net_events.patch](../greensim/action_feed_net_events.patch)` к моему `action_feed.py`. С `--feed.adaptive-detector net` события ищутся по чистому ходу пальцев в окне ±4 строки (порог 0.15 рад): дрожание в окне взаимно гасится, а настоящее закрытие кисти остаётся. Проверила на самом `action_feed.py`: при шуме 0.01 рад старый детектор оставляет на 1× 100 % строк, новый 63 %, как на чистом плане.

## B. Опережение действия в данных (CPU, несколько минут)

```bash
python -m gch.inspect_wbc <scene root> --out wbc_report.md
```

Раздел «How far `action` leads `observation.state`» показывает опережение в кадрах по группам суставов. Это δ_demo в формуле (кадры / 30). Его стоит сравнить для scripted- и teleop-сцен. Если у teleop оно другое, дообучение на teleop меняет встроенное опережение плана, и это второй путь, которым ft1 мог потерять темп.

## C. Темп в замкнутом контуре (мой бенч на сервере)

Бенч у меня на сервере уже поднят, нужно только включить рекордер (`GC_RECORD_DIR`).

```bash
# бейзлайн на скорости 1.0 и 1.3 с записью
GC_RECORD_DIR=rec_s100 SEEDS=42 VARIANTS=bench/variants_baseline.txt bash bench/run.sh ~/green_sim full
GC_RECORD_DIR=rec_s130 SEEDS=42 VARIANTS=<файл со строкой fast130> bash bench/run.sh ~/green_sim full

python greensim/tempo_probe.py demo --data <ring/darkstore/plate root> --out demo.json
python greensim/tempo_probe.py sim --rec rec_s100 --out sim100.json
python greensim/tempo_probe.py sim --rec rec_s130 --out sim130.json
python greensim/tempo_probe.py compare demo.json sim100.json --speed 1.0
python greensim/tempo_probe.py compare demo.json sim130.json --speed 1.3
```

`tempo_ratio` — медианная скорость суставов руки в замкнутом контуре, делённая на медианную скорость в демонстрациях. Обе считаются по кадрам с движением с шагом 0.24 с, как пишет рекордер. Скрипт обращает формулу и выдаёт отставание симулятора `delta_sim_inferred_s` и скорость, которая закрывает дефицит.

Что ожидаю: на скорости 1.0 `tempo_ratio` заметно ниже 1 (по стенду 0.8–0.9), на 1.3 около 1. Если на 1.0 темп уже около 1, то fast130 выиграл не за счёт компенсации дефицита.

Заодно стоит посмотреть разбивку `results.json` по подзадачам для baseline и fast130: она покажет, выиграл ли fast130 за счёт времени или за счёт числа выполненных подзадач.

## D. Что можно проверить сабмитами

В порядке убывания ожидаемой пользы (по результатам TempoBench, README §5):

1. **Адаптивная скорость с исправленным детектором**, если A2 покажет, что старый детектор на 1× держит почти все строки. Варианты `--feed.adaptive-speed 1.5 --feed.adaptive-detector net` и 2.0, оба с поднятым пределом ускорения, как в `adaptive15_acc` / `adaptive20_acc`. В стенде при большом отставании робота это лучше любого равномерного ускорения (0.77 против 0.63), при совпадающем немного хуже (0.95 против 1.05). Ожидаю, что будет не хуже fast130.
2. **Дообученный чекпойнт с калиброванной скоростью.** Если A покажет у ft-чекпойнта темп k < 1 относительно бейзлайна, его надо отправлять со скоростью около 1.3 / k, а не 1.3. В стенде такая калибровка возвращает 82–93 % потерь дообученных моделей.
3. **Порог застывания.** Строки плана заканчиваются через `lead + 50·row_dt = 0.03 + 1.667/s` с, а в бленде план живёт 1.2 с. При s > 1.425 самые старые планы доживают до последней строки, застывают на ней и тянут уставку назад. Мой патч уже выкидывает такие планы для адаптивной скорости (`_expired`), а для равномерной нет; исправление в одну строку: при `times is None` сравнивать возраст плана с `lead + len(rows)*row_dt`. В стенде это почти ничего не даёт (не больше 0.03), потому что спад на больших скоростях определяется моментом закрытия схвата, а не застыванием. Так что этот сабмит имеет смысл, только если fast150 и выше упадут резко.
